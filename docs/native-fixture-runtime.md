# Native mixed-source reproduction

`fixture_plan` now declares PostgreSQL, Elasticsearch and Kafka reads together. Use explicit multi-column relations and matches, including tenant columns. Names alone remain candidates. `service` adds cached passport obligations; `requiredReads` can add reviewed dependencies that must be bound. An unbound source, changed mapping/settings, truncated event/document window, missing required entity, unsupported payload schema or unsafe numeric value prevents completeness. Exact big integers and decimals use strings; wire JSON that would silently lose numeric precision is rejected.

`fixture_capture` uses one read-only repeatable-read transaction per PostgreSQL database. ES uses a point-in-time search; Kafka uses bounded partition windows. `consistencyMode:"verify"` independently rereads captured SQL queries and records changes. These observations are not a distributed snapshot or distributed transaction. Hashes protect exported SQL, ES mappings/settings/documents and Kafka schemas/envelopes/windows in test resources. `scenario_state_plan/capture` can bind the ES part of an existing mixed fixture separately.

To replay, place a reviewed profile outside imported resources, for example `dev/native-fixture.json`:

```json
{"version":1,"adapter":"native-containers","readyTimeoutMs":180000,"kafka":{"allowOffsetRemap":true}}
```

The defaults require existing `postgres:16-alpine`, `docker.elastic.co/elasticsearch/elasticsearch:8.17.3` and `docker.redpanda.com/redpandadata/redpanda:v24.3.6` images. `images` overrides are reviewed profile data, with fixed adapter commands. Images are inspected and run by immutable image ID; no automatic pull occurs. The profile schema is `/contracts/v1/fixture-runtime.schema.json`. Kafka replay defaults to `auto`: decoded object/array payloads are JSON encoded, UTF-8 strings retain their wire text. Explicit `codec:"json"` or `codec:"string"` selects one encoding for both sides. It supports JSON/string keys and values, UTF-8 headers, tombstones, empty strings and partitions. Original offsets/timestamps remain in hashed envelopes and replay mappings; actual broker offsets/timestamps are new and require the explicit remap policy. Avro/protobuf encoded payloads and nested ES mappings require another adapter and fail explicitly.

Call the separate tools in this order:

1. `fixture_runtime_preflight({workspace,directory,profile})` checks resources and dependencies.
2. `fixture_runtime_start({workspace,directory,profile})` starts/polls one job and returns a durable runtime lease; poll with `{job}`.
3. `fixture_runtime_bindings({id})` supplies temporary loopback PG/ES/Kafka endpoints. PG bindings use an application role without permission to alter the independent audit journal.
4. `fixture_runtime_arm({id,contract})` freezes exact effects before running the actual application or project tests. Each source assertion selects `pg:<db>:<schema.table>`, `es:<index>` or `kafka:<topic>` and supplies `noWrites:true` or exact `rows`/`added`/`removed` arrays. Unlisted observed effects fail by default. An already armed contract cannot be rewritten to fit a result.
5. Run the actual service/tests with those bindings. For a Kafka entrypoint, `fixture_runtime_publish({id,topic,message})` triggers only a declared topic in the owned broker after expectations are armed. Existing `test_run` SQL fixture loading remains a distinct path; a native dependency start does not imply application execution or a remote dev target.
6. `fixture_runtime_observe({id,source?,limit?,offset?})` independently checks one source or all sources. `fixture_runtime_check({id})` evaluates the frozen contract and a quiet window. Both return compact summaries and interactive full-evidence views.
7. `fixture_runtime_stop({id})` removes only containers/network with matching ownership and image evidence. `fixture_runtime_cleanup({})` recovers expired leases. Cleanup failures remain retryable; stopping during startup requests compensation before resource creation continues.

Postgres observations include a protected journal of committed row writes and TRUNCATE statements, so a committed update followed by a compensating update cannot satisfy `noWrites`. ES index identity, indexing/deletion counters and document sequence metadata detect create/delete and update/revert even when the final document set is equal. Broker observations consume actual replayed records. These are explicit protocol scopes: uncommitted PG attempts, arbitrary undeclared tables, ES operation histories across an unobserved process restart, broker retention/compaction and distributed commit under failures are not exhaustively proven. The Docker network is an owned bridge with loopback published ports; outbound access is not blocked. Source environment endpoints are never replay destinations. Unknown runtime reads remain separate inventory gaps.

Run fast checks with `node --test test/reproduction-native.test.js`. Run the disposable native integration with `DT_TEST_NATIVE_FIXTURE=1 node --test test/reproduction-native.test.js`; it creates and cleans its own resources and leaves unrelated containers untouched. Native readiness records exact image identities, startup timing and independently observed effects rather than inferring success from a project report.

Measured evidence from the disposable test on the shared 8GB Docker VM is in [native fixture readiness](evidence/native-fixture-readiness.json): 149,245 ms cold dependency startup and approximately 250 s for the latest full adversarial execution/cleanup; the preceding run measured 177,158 ms and approximately 274 s. This is separate from warm cached-tool latency. The shipped default readiness deadline is 180 s (reviewed profiles can allow up to 300 s), and startup returns a resumable job rather than requiring a long synchronous client connection. A future fast reset/pool must preserve per-test index/topic/database isolation and protected observer ownership before replacing independent container creation; source snapshots and broker delivery guarantees do not follow from faster setup.
