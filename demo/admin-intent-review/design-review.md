# Admin intent review — independent design assessment A

Method: independent Assessment A (`/root/admin_design_review`), completed without detector output or Assessment B findings. Baseline: `5a8ba086dde01702b4351ff84be6df12d9339538` (verified against the checkout). This is the design assessment input to the parent review, not the combined critique.

## Verdict

Admin has unusually good product substance: exact source identities, retained evidence, revision checks, explicit execution, and distinctions between static inference and runtime proof. Its presentation makes users learn the tool's internal organization before they can benefit from that substance. The main design problem is the route from a task to the next justified action, not a need for a new visual identity.

The restrained typography, blue action color and compact data treatment suit developer work. Preserve that vocabulary. Replace the feature-led entry structure with a persistent task and evidence workspace, while retaining direct access to the existing expert surfaces. The desired shift is from “which of these 22 areas contains the tool?” to “what do I know about this task, what remains uncertain, and which action will resolve it?”

## Strengths to preserve

1. **Evidence honesty.** Project knowledge explicitly distinguishes declared/static paths from runtime traces, names gaps and pins source. The map distinguishes candidates and annotations. Preserve those distinctions in every proposed overview, badge and graph; simplify their presentation without flattening their meaning. Evidence: `context-project.jpg`, `map-initial.jpg`; `web/admin-project-context.js`, `web/admin-map.js`.
2. **Explicit actions and durable outcomes.** Preparing a tool does not run it; reading a saved result does not replay it. Workbench and API code handle background work, disconnected acknowledgements and capture failure as separate outcomes. Revision checks protect edited publications and files. These are appropriate foundations for trust. Evidence: `context-tool-prepared.jpg`, `context-tool-result.jpg`, `api-initial.jpg`; `web/admin-workbench.js`, `web/api-explorer.js`, `web/admin-context.js`.
3. **A capable expert path.** Structured controls coexist with exact JSON, scripts, copied invocations and retained results. Do not replace this with a chat-only interface or remove deep tools during navigation simplification. Evidence: `scripts-editor.jpg`, `studio-initial.jpg`, `semantic-settled.jpg`; `web/admin-ux.js`, `web/studio.js`.

## Five priorities

### 1. Make the selected task the organizing object — P1

**Problem.** The global header asks for a freeform `Chat / task` ID while Workbench independently defaults to `Session only`, Context shows task folders, Studio creates durable continuation memory, and Task desk opens autonomous task runs. All are legitimate concepts, but the screen does not explain how the current work relates to them. The same “start/resume task” intention has several entry points. Twenty-two sibling areas remain visible, with seven entries under Investigate, eight under Work and six under Operate; Self-reflection precedes those groups. Group labels help scanning but do not reduce the number of competing destinations.

**Evidence.** `workbench-initial.jpg`, `context-initial.jpg`, `studio-initial.jpg`, `reflection-initial.jpg`. The UI composition and 22 destinations are explicit in `web/admin-ux.js:35`; identity handling is in `web/admin-runtime.js:1`; the separate durable-task creation is in `web/studio.js:3`. This is an observed conceptual conflict and a source-supported structure, not a claim that identities are incorrectly authorized.

**Proposal.** Start with recent tasks and one obvious new-task action. A task workspace keeps its title, environment, repository/source revision, evidence destination, latest state and next question visible. Show the story/scope ID as technical detail within that task. Offer four stable global destinations — Tasks, Services, Library and Operations — with existing areas reachable inside them and through direct links/search. Task-local navigation should be about Overview, Evidence, Work and Activity; reduce initial decisions further by making one current action primary. A user can still deliberately work without saving to a task.

**Acceptance.** A first-time developer and tester can choose an existing task or start a new one in at most two deliberate decisions, without learning “context” versus “continuation.” Within a selected task, an action's evidence destination is visible before execution. Switching services/tools does not silently create another task or require retyping its ID. Existing bookmarked URLs and expert tool access remain available.

### 2. Replace schema-shaped primary flows with narrow task editors — P1

**Problem.** Joern & ports initially renders a roughly 6,147 px page at a 1,280 px capture width. The `from` and `to` objects each expand alternatives including IDs, analyses, repository, SHA, signature, file coordinates, code, database, Kafka and HTTP identity. A simple call-path question becomes dozens of choices before Run investigation. The seven task presets sit above an eight-tool selector, followed by a second operation selector. The structured form is technically preferable to raw JSON but still exposes the schema's union rather than the user's decision.

**Evidence.** `semantic-settled.jpg` and `work/admin-intent-review/semantic-settled.txt`. `semanticAdminPrepare` builds `from`/`to` defaults in `web/admin-semantic.js:23`; `semanticStructuredForm` mounts the full schema in `web/admin-ux.js:23`. The screenshot/DOM establish form breadth. They do not establish that tracing fails.

**Proposal.** Select the question first: find symbol, follow calls, follow values, map boundaries, compare revisions, or correct a boundary. Resolve exact service/source/analysis identity once, then show it as a compact selected-source summary. For a path, show two symbol pickers, one mode and an explicit analysis status. Let the user choose an alternate endpoint kind when required; render only its applicable fields. Put limits, engine details and exact JSON in Advanced. Keep Run and validation near the edited fields or in a stable task action bar.

**Acceptance.** A common retained-source call-path investigation can be prepared with no more than four primary inputs after selecting source. Selecting an endpoint by method does not expose database/topic/HTTP fields. Missing analysis explains the exact prerequisite and offers a separate build action. Changing the action preserves a restorable draft rather than forcing the user to reconstruct it.

### 3. Make an outside-in evidence chain visible and actionable — P1

**Problem.** The necessary capabilities already exist but their route is obscured. Explore starts at a blank search and its first instruction only describes Postgres line selection. A service opens another passport page. API client has a useful Database inspector, but it is collapsed beneath a blank New request state. Services map initially shows name-prefix containers without relationships in the current slice; Tool map fits all 318 tools into a graph too small to read. None of these starting views gives a developer investigating a wrong displayed name a compact chain from the actual record to API response, source transformation and verified fix.

**Evidence.** `explore-initial.jpg`, `api-initial.jpg`, `map-initial.jpg`, `capabilities-initial.jpg`. `web/admin.html:642` produces usage links and `web/api-explorer.js:571` opens the database inspector; `web/api-explorer.js:587` runs a read-only query and can add it to a workflow. The path exists in parts. Missing integration and weak default discovery are the finding; absent capability is not.

**Proposal.** A task's investigation panel accepts a symptom or starting object and offers a small number of relevant starts: a record/field, API request or source symbol. For the DB path, browse cached schema and usage first, show freshness, prepare a bounded read, retain the selected row and exact keys, then prepare the relevant API request. Keep response fields and the selected DB fields side by side. Follow the named transformation into pinned source/Joern evidence and mark each relation as observed, static, declared or unresolved. Each evidence item offers one explicit next inspection and an optional expert tool menu. The graph shows the selected service's neighborhood; all-tools and estate overviews become optional exploration modes.

**Acceptance.** The demo supports a complete wrong-person-name investigation: select task → inspect record → call API → compare fields → inspect transformation → review corrected mapping/selection → rerun the bounded check → retain a reproducible handoff. Every step retains environment and concrete identifiers, and shows what was measured versus inferred. No live call is triggered by opening a saved item. The user can return to the selected evidence without searching for it again.

### 4. Show task outcomes and needed intervention before raw execution detail — P1

**Problem.** History presents many rows of tool names and JSON arguments; Runtime presents the same work as execution records, followed by a second Stored metadata list; Jobs is another destination. Autonomous runs live in Task desk. These layers serve different purposes, but the initial composition does not answer the returning user's question: “What happened overnight, what changed, and what needs me?” A technical `done` or `ok` can also be mistaken for task success, despite good explanatory copy elsewhere.

**Evidence.** `history-initial.jpg`, `runtime-initial.jpg`, `jobs-initial.jpg`, `studio-initial.jpg`. `web/admin-runtime.js:57` renders execution state, ownership, resources and cleanup; `web/admin-scripts.js:616` renders history; `web/tasks.js:81` handles task runs. This is a hierarchy/integration finding. The code already has valuable controls and unknown-outcome handling.

**Proposal.** Each task's Activity starts with a short state summary: current objective, checkpoint, completed checks, failed/unknown outcomes, next decision, and active resource leases. Group child calls under their task step. Show needs-attention and incomplete cleanup ahead of successful routine calls. Use separate labels for invocation completed, application verdict, test verdict and task completed. Keep cancellation and observation of the existing run together, with links to full Runtime/Jobs detail. History should summarize calls in compact rows, expand exact arguments on demand and retain its “save repeated work” capability.

**Acceptance.** A user resuming an overnight task can identify the failed step, inspect its retained input/result, choose retry/repair/continue, and copy the resulting handoff without rerunning completed work. A lost acknowledgement visibly differs from a failed action. Cancel remains pending until owned work and cleanup settle. Task completion is never inferred solely from an HTTP 200, a green invocation badge or static path reachability.

### 5. Give edits and corrections one reviewable draft-to-publication pattern — P1

**Problem.** Editing is spread across Context metadata/file saves, staged Project knowledge edits, global Architecture publication, map corrections, semantic port corrections, scripts, page definitions and raw configuration. Source contains strong version protection, but the visible workflow varies. For example, Context's top Save context button and bottom Save file button are separated by a long editor; the unsaved marker names neither scope. Project editing exposes staging followed by publication well below several forms. The Architecture empty state immediately offers a global publication form and a large blank preview.

**Evidence.** `context-dirty.jpg`, `context-project-edit.jpg`, `architecture-initial.jpg`, `scripts-editor.jpg`. `web/admin-context.js:25` saves metadata, `web/admin-context.js:156` saves files, `web/admin-project-context.js:24` stages flow changes and its publication handler uses expected revision; `web/admin-architecture.js:9` publishes globally. Guard behavior is source-reviewed, not successfully reproduced in this browser session.

**Proposal.** Use the same three visible states: Saved evidence → Local draft → Reviewed publication. The draft bar identifies exactly what changed and where Save applies. Private task notes have a local save; shared corrections require a review view showing detected evidence alongside the proposed correction, exact source/revision, reason and publication audience. Preserve immutable history and make restore create a new revision. Explain conflicts with local/server comparisons and actionable merge/reload choices. Keep a separate expert JSON editor without making it the primary correction flow.

**Acceptance.** A user can correct a false/missing service connection in the task, review the diff and reason, publish deliberately, then reopen the same original evidence and the published correction separately. Saving a note cannot be mistaken for publishing shared knowledge. Navigation/reload tests prove each supported draft is either retained or explicitly discarded. This requirement does not assert that the captured automation stall was an application failure.

## Cognitive load and emotional journey

The intrinsic work is complex: matching a deployed symptom to database data, API behavior, static code, a selected revision and a reproducible test. Admin should support learning those relationships. Making the user reconstruct where each relationship lives is avoidable load.

| Checklist | Result | Evidence |
|---|---|---|
| Single focus | Fail | Global area navigation and nested work/tool modes compete with the current investigation. |
| Chunking | Fail | Main groups have 7/8/6 destinations; semantic endpoint shapes expose many alternatives together. |
| Related information grouped | Partial pass | Cards and split panes are consistent, but a single investigation crosses several apps and scopes. |
| Clear visual hierarchy | Fail | Empty main panes and complete-fit graphs receive major space while task/next action is absent. |
| One decision at a time | Fail | Source identity, task identity, tool, operation and endpoint representation appear before one question is resolved. |
| Minimal choices | Fail | 22 global areas; 13 tool-map categories; 7 semantic presets plus 8 tools plus operation choices. These are distinct decision points, not one additive count. |
| Working memory support | Fail | The task's chosen record, source revision, comparison and next question are not consistently pinned across the chain. |
| Progressive disclosure | Partial pass | Advanced JSON, raw results and guides are usefully collapsed, but semantic object alternatives remain fully exposed. |

Six clear failures indicate high cognitive load under the skill's rubric. This does not mean “density is bad.” Dense schema/results tables are appropriate when they help compare real evidence. The waste is repeated choice and mental context transfer.

At the start, the user sees a technically capable system but must invest in its vocabulary before acting. The likely emotional valley is preparing an investigation while wondering which identity/source is current. The strongest moment is a retained result with explicit source/gaps: the tool has made the uncertainty auditable. The end is weaker because handoff, final verdict and pending cleanup are distributed. A task summary that names the answer, supporting checks, unresolved gaps and next step would give the work a clear ending without pretending uncertainty is resolved.

## Persona walkthroughs

These are task-based reviews derived from the user's stated workflows, not observed usability sessions.

- **Developer investigating an incorrect person name.** Starts with a UI/API symptom, needs the actual record and exact transformation, then a regression check. Red flags: several plausible “start” areas; collapsed DB inspector; lack of a continuously visible record/API/source comparison; technical invocation `ok` mistaken for a proven correction. Success is a retained chain with exact inputs, source identity, corrected behavior and test evidence.
- **Tester preparing or reproducing a defect.** Needs data that agrees across service edges, a reproducible request, expected/actual values and safe reuse tomorrow. Red flags: a cached/static path shown without immediate evidence type; separate locations for script, result, page and task memory; generic forms demanding CPG details before the tester has selected the entry point. Success is a reusable case with prerequisites and unresolved gaps, and no hidden replay when opening it.
- **Impatient power user/maintainer.** Knows tool names and wants to search, copy, compose and observe many runs. Red flags: a navigation simplification that hides direct tools; forced instruction; reentering identities; all-tools graph as a mandatory intermediate step. Success is task-first defaults with command search, deep links, exact JSON, scripts and direct diagnostic panels retained.
- **Accessibility cross-check.** The source supplies roles, labels, focus treatment and keyboard activation for parts of Admin; preserve that work. The remaining risk to verify is practical focus order through long generated forms and iframes, accessible naming of repeated endpoint controls, keyboard operation of graph/tree actions, and recovery dialogs. No conformance failure is asserted without exercising these states.

## Proposed interaction contract for the separate demo

The separate demo should prove the workflow, not just show a shorter sidebar. It can use the current system font, neutrals, blue selected/action states, table density and semantic badges. Stronger hierarchy is sufficient; adding decorative cards, gradients or large status numerals would not solve these findings.

1. **Task entry.** Recent tasks show the question, current verdict/state, environment/source, latest evidence and next decision. New task asks for title and starting resource. Resolve technical story/context/continuation relationships behind the task and expose them in details.
2. **Investigation.** Keep task/source summary at the top, evidence chain on the left and one focused inspection in the main area. A selected DB row can prepare the API request; an API field can open the relevant source evidence. Every step records inputs and whether the result was observed, static or declared. The user can always open the exact tool and arguments.
3. **Correction.** Open the current finding beside the proposed edit; show source pin, reason, audience and revision. Save private draft separately from Publish correction. After publication, the original detected finding remains inspectable.
4. **Verification.** A check compares expected and actual values, names the execution target and dependencies, and distinguishes unit/mock proof from real entry-to-exit effects. It reports changed behavior, remaining gaps and evidence links.
5. **Resume and handoff.** A returning task opens at its last checkpoint with active/failed/unknown work grouped by step. “Observe existing run” is distinct from Retry. Handoff includes task objective, source pins, concrete inputs, observed outcome, reproduction recipe, evidence and next decision.

Task-first does not require removing Services, Library or Operations. Services supports estate/resource exploration; Library holds shared knowledge, scripts/pages and reusable cases; Operations holds live diagnostics/configuration. A service or library object can be attached to the active task, and expert users can open it independently.

## Rollout and acceptance

**Stage 1 — isolated reviewable demo.** Implement both complete flows using explicitly labeled fixture data: (a) wrong-person-name DB/API/source investigation with a reviewed correction and retained verification; (b) resume an overnight task with a failed/unknown step, recovery, cleanup visibility and reproducible handoff. Include empty, loading, running, saved, failed, conflict, cancelled and needs-attention states appropriate to each flow. No production navigation change is necessary to review this.

**Stage 2 — validate the interaction contract.** Walk through those two tasks with a developer, tester and power user. Verify the first useful action, scope comprehension, evidence continuity and recovery; collect task completion and wrong-turn observations. The current assessment has no measured timing baseline, so any claim of percentage improvement must wait for those observations. Validate desktop at 1,280/1,440 px and a narrow layout, 200% zoom, keyboard-only operation and screen-reader labels/status. A phone can prioritize monitoring/review; it should not be required to display the full desktop editor structure.

**Stage 3 — additive production route.** Introduce the task workspace behind a reversible opt-in route, using existing tool contracts and durable records. Keep old URLs and direct tool access. Migrate one complete evidence chain before moving the remaining areas. A production adoption gate is evidence that an existing task can be reopened with no lost files, drafts, saved results, revisions or execution links, and that copied reproduction recipes resolve to the same source and concrete inputs.

**Stage 4 — consolidate navigation only after continuity holds.** Move the 22 areas into the four destination structure. Align save/result/status patterns, then remove duplicated chrome. Do not defer scope clarity, error recovery or cleanup visibility as visual polish; they are part of the core contract.

Acceptance checklist for the two demo flows:

- Selected task, evidence destination and exact source are visible through every inspection.
- Opening saved evidence does not query live systems or repeat effects; running and publishing require deliberate labeled actions.
- The wrong-name chain can be followed forward and backward without copying/retyping IDs or losing the selected record.
- A correction displays original evidence, proposed change, reason, expected revision and audience before publication.
- Completed tool invocation, application result, test proof and task completion use distinct labels.
- Unknown acknowledgement, capture failure, validation failure, version conflict and cleanup failure have distinct recovery routes that preserve work.
- Overnight progress opens at the latest checkpoint; existing-run observation is the obvious first recovery action.
- One handoff contains exact environment/source/inputs, result/expected value, relevant evidence, runnable recipe and unresolved gaps.
- Expert search, exact JSON, scripts, direct URLs and full Runtime/Jobs/Config remain accessible.

## Minor observations and follow-up questions for synthesis

- Duplicate generated/embedded headings in Studio and Pages spend the first viewport on repeated identity; remove one layer when composing the task workspace.
- Fixed blank Architecture and embedded-app frames make empty pages feel unfinished. Size previews to actual content, hide an empty preview, and show a purposeful starter state.
- User-facing schema labels such as `analysis Id`, `node Label` and `revision Key` should have deliberate task wording while exact API keys remain in Advanced.
- Use task/result titles such as “Checkout record versus API name” instead of `find: result`; the exact tool name remains available in details.
- Graph overview counts need to explain completeness and selection, but should not replace an actionable focus. “No relations in this slice” must never imply no real dependency.
